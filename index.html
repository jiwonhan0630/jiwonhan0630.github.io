Attribute 기반의 자동 이벤트 바인딩 시스템

UIToolkit 환경에서, element class를 통해 이벤트를 자동으로 바인딩하는 기능을 구현하였습니다. 디자이너는 UI를 새로 만들거나 수정할 때, element class를 추가하면 즉시 기능을 적용할 수 있으며, 프로그래머는 Attribute를 선언하는 것으로 추가 바인딩 작업 없이 이벤트를 바인딩할 수 있습니다.

[ElementCommand("cmd--button--brush-tool")]
private static void SelectBrushTool(VisualElement target) => History.Log("브러쉬 도구를 선택하였음");

고민의 흔적

처음 고민한 것은 '어떻게 하면 작업 영역을 벗어나지 않고 협업하는 시스템을 만들까?'였습니다. 그동안 여러 편의 기능을 개발하며, '무언가를 개선하기 위해 새로운 툴과 프로세스를 만들었지만, 작업 절차 자체를 줄일 수는 없을까?'라는 의문이 자연스레 생겼습니다. 따라서 이번에는 각 직군이 '원래 하던 일'에 최대한 자연스럽게 녹여보자는 것을 목표로 삼아 설계를 진행했습니다.

먼저 각 직군이 UIToolkit과 UI Builder를 '실제로 어떻게 사용하고, 어디서 불편함을 느끼는가?'를 검토했습니다. UI 설계 문서를 기준으로 삼아, 디자이너는 UI Builder에서 화면과 요소를 구성하고, 프로그래머는 코드에서 동작을 구현하고 에디터에서 이벤트를 연결한다는 작업 흐름을 확인했습니다.

UI 디자이너가 element class를 식별자처럼 사용하고 있다는 점에 착안해, 이것을 이벤트 바인딩 키로 활용하는 구조를 구상했습니다. 프로그래머는 에디터에서 직접 바인딩하지 않고, 각 함수에 Attribute를 선언하는 것으로 해당 요소와 이벤트가 자동으로 연결되도록 설계했습니다.

기능 구현 시에는 Attribute 탐색을 위한 Reflection과 UQuery 사용을 초기화 시점에 단 한 번만 수행하도록 구성하여, 런타임 중 발생할 수 있는 비용을 줄였습니다. 또한 이벤트 등록 과정에 static 람다 등을 사용하여 외부 변수 캡처로 인한 추가 GC 할당을 방지하였습니다.

넘버링 시스템

에셋 타입 기반 유효성 검증

선택된 에셋의 타입(Texture, AudioClip, Material 등)을 판별하여 사전에 정의된 고유 Prefix 규칙을 자동 매핑합니다. 정규표현식을 활용하여 공백이나 허용되지 않는 특수문자 등의 예외 규칙을 걸러내고, 유효하지 않은 문자는 자동 제거 또는 사전 합의된 규칙 문자로 안전하게 치환합니다.

확장성을 고려한 아키텍처 설계

네이밍 로직 전체를 Abstract Class로 정의하고, Light, Texture 등 개별 에셋/컴포넌트 타입이 이를 구현하여 상속받도록 결합도를 낮추었습니다. 개방-폐쇄 원칙을 준수하여 새로운 에셋 규격이나 컴포넌트 타입이 추가되더라도 기존 코드를 수정할 필요 없이, 해당 네이밍 구현체를 추가 정의하는 것만으로 손쉽게 기능 확장이 가능하도록 설계했습니다.

고민의 흔적

처음 고민한 것은 '네이밍 규칙에 따라 이름을 적용하는 과정 자체를 줄일 수는 없을까?'였습니다.

아트 리소스는 관리 시트를 통해 이미 네이밍 정보가 정리되어 있었고, 프로젝트 내 에셋과 연결되면서 네이밍에 활용할 수 있는 정보도 자연스럽게 만들어지고 있었습니다. 하지만, 그러한 리소스를 엔진 내에서 사용할 때에는 별도의 네이밍 규칙을 다시 확인하고 규칙에 맞는 이름을 직접 입력하는 과정이 반복되고 있었습니다.

이러한 작업에 불편함을 느끼는 경우가 여러 번 발생했고, 이를 해결하기 위해 고민을 거듭하다 '기존에 존재하는 정보를 활용한다면, 규칙에 맞는 이름을 만들어줄 수 있지 않을까?'라는 생각이 떠올랐습니다.

GameObject의 컴포넌트 구성과 참조 중인 원본 리소스, Mesh·Material, 에셋 타입, 하이어라키 내 순서 등 프로젝트 내부에서 확인할 수 있는 정보를 이름 생성에 활용했습니다. 다만 오브젝트마다 이름을 결정하는 데 필요한 정보가 다르기 때문에, 하나의 기준을 일괄적으로 적용하기는 어렵다고 판단했습니다.

이에 별도의 설정 창에서 네이밍에 사용할 컴포넌트와 정보, 적용 우선순위를 직접 지정할 수 있도록 구성하고, 설정된 기준에 따라 필요한 정보를 조합하여 이름을 생성·선택 후 일괄 적용하도록 설계했습니다.

이후 실제로 사용해보았을 때, 에셋 하나에 이름을 적용할 때마다 창을 열어 사용하는 것은 불편하다고 판단했습니다. 이에 개별 적용 기능을 각 에셋의 컨텍스트 메뉴로도 제공하여, 작업 흐름을 크게 벗어나지 않고 바로 사용할 수 있도록 구성했습니다.

CSV Utility

별도의 파싱 코드 작성 없이 CSV 데이터를 C# 컬렉션 및 오브젝트로 자동 변환하는 컨버터 유틸리티를 구현했습니다. 헤더 이름 매핑과 열 인덱스 매핑을 모두 지원했습니다.

public class Weapon
{
    [CSVIndex(0)] public string ItemCode;
    [CSVHeader("wpn_author")] public string AuthorName;
    public List<string> EnchantList;
    public EquipSlotType SlotType;
}

컨버터 클래스를 상속하여 복잡한 자료형(2중 딕셔너리 등)도 CSV 포맷 안에서 직접 구조화하여 파싱할 수 있게 지원했습니다.

Addressables 시스템 확장

프로젝트의 Addressables 적용 방식에 맞춘 커스텀 래퍼 클래스와 커스텀 인스펙터를 구현했습니다. 이를 바탕으로 에셋 참조 규칙과 라이프사이클 관리 구조를 정비하고, Global/Stage 단위 참조 카운팅으로 에셋의 로드·언로드 흐름을 관리했습니다. 예제가 포함된 가이드라인을 공유해 팀원이 일관된 방식으로 에셋을 적용할 수 있도록 지원했습니다.

트러블슈팅

지형 생성 시간 단축 및 메모리 최적화

GC Allocation 제거 및 청크 기반 연산 최적화를 통해 맵 생성 시간을 96% 단축했습니다.

문제 상황

기획상 요구되는 최대 크기 환경에서 거대한 레벨을 생성할 경우, 380초의 긴 시간이 소모되는 현상이 발생하였습니다.

원인 분석

Profiler를 사용하여 분석한 결과, 심각한 GC 오버헤드와 비효율적인 연산이 핵심 원인으로 파악되었습니다.

  1. GC 오버헤드:
    • class 기반 좌표 클래스의 연산자 오버로딩으로 인해 매 연산마다 발생하는 힙 할당
    • ToList, ToDictionary 등의 잦은 LINQ 호출로 인한 리사이징과 박싱
    • 잦은 Coroutine 호출
  2. 비효율적 알고리즘:
    • 오버랩 체크 시 타일 개수만큼 객체를 생성하거나 전체를 순회하는 O(N^2) 로직
    • 동일한 결과를 반환하는 조건 연산의 중첩 사용

해결 과정

1. GC 오버헤드 제거

좌표 클래스를 구조체로 변경하는 동시에 지형 정보를 담고 있던 string 등 참조 타입의 변수를 제거하고, LINQ 사용으로 인해 발생하는 문제점을 해결하기 위해 아래와 같이 수정하였습니다.

  • 컬렉션을 미리 생성함과 동시에 Capacity를 계산하여, 함수 내에서의 생성과 Resizing을 최소화하였습니다. (Memory Profiler를 통해 예약된 메모리와 컬렉션의 최종 크기가 동일함을 검증했습니다.)
  • 쿼리 함수를 for/while를 사용한 순회로 변경하여 새로운 컬렉션을 생성하지 않도록 하였습니다.
  • List 순회 대신 HashSet과 Dictionary을 사용하여 평균 데이터 접근 속도를 개선하였습니다.

마지막으로 코루틴은 컴파일 단계에서 클래스로 선언되어 작동하기 때문에 GC.Alloc이 일어나게 되므로, 이를 방지하기 위해 구조체 기반의 UniTask를 도입하였습니다(솔직히, 개인적으로 사용하고 싶었던 라이브러리인 점도 있었습니다).

2. 청크 시스템 적용

청크 시스템의 Spatial Hash Grid를 적용하여 좌표 단위로 실행하는 동작을 영역 단위로 실행하도록 수정하였습니다.
오버랩 체크, 영역 회전, 확장 등 관련 함수의 호출 횟수와 평균 데이터 접근 속도를 개선하였습니다.

3. CPU Friendly

개선된 구조에서도 일부 함수는 최악의 경우 수십만번 이상 호출되어 실행 시간에 영향을 주는 것을 확인하였습니다. 더 이상 호출 횟수를 줄이는 것은 어려웠기 때문에, 함수 자체의 동작 시간을 줄이기 위해 아래와 같은 방법을 통해 CPU의 처리 시간 감소를 도모하였습니다.

  • 좌표 구조체의 크기를 조절하여 메모리 접근 횟수를 줄였습니다.
  • 불필요한 중간 객체를 제거하고 함수 파라미터에 수식을 직접 넣어 전달하였습니다.
  • 연산자 오버로딩을 제거하고 멤버의 값을 수정하는 연산 함수로 변경하였습니다.

결과

모든 청크 검사 실패와 기획상 최대 지형 크기 적용 등을 가정한 동일한 테스트 환경에서, 소모 시간이 380초 → 14초로 96% 단축되었습니다.
또한 Profiler로 측정 결과, 핵심 생성 로직에서의 ZeroAllocation을 달성하고, GC Spike 현상을 개선할 수 있었습니다.

NavMesh 환경에서 WheelCollider 적용

NavMesh를 사용하는 월드에서 작동하는 WheelCollider를 이용한 주행 기능을 구현하였습니다.

문제 상황

차량의 이동 방식을 NavMeshAgent에서, 물리가 적용된 WheelCollider로 변경해야 했습니다.
기존 NavMesh 데이터를 활용하면서도, 물리 엔진 기반의 주행이 가능한 시스템을 새롭게 구축해야 했습니다.

해결 과정

1. NavMesh 데이터 추출 및 AI Navigation 동작 분석

Unity AI Navigation Package의 Baking 함수를 추적하여, 베이킹 시 생성되는 NavMesh 폴리곤의 좌표 데이터를 추출하는 기능을 구현했습니다.
추출된 데이터를 별도의 ScriptableObject로 저장하여, 런타임에 경로 데이터를 참조할 수 있도록 구조화했습니다.

2. 주행 경로 수정

NavMesh가 지원하는 경로 따라가기 함수 사용 시 폴리곤의 꼭짓점 부분을 이용하여 이동하기 때문에 시각적으로 부자연스러운 문제가 발생하였습니다.
이를 해결하기 위해 삼각형의 무게중심을 선형 보간한 경로를 사용하였으나, 삼각형 형태에 따라 불필요한 움직임이 발생했습니다.
최종적으로는 인접한 폴리곤이 맞닿는 모서리의 중점을 연결하여 경로를 수정하는 로직을 적용하여, 차량이 도로의 중앙을 따라 부드럽게 이동하도록 구현했습니다.
또한 Box, Capsule 등 장애물을 감지하면 Raycast를 통해 우회 경로를 생성하도록 구현했습니다.

3. 조향 및 감속 제어 구현

차량의 속도와 경로 곡률에 따른 조향·감속 처리를 구현하기 위해 차량 제어 관련 자료를 조사하고, 참고한 제어 수식을 WheelCollider 기반 주행 구조에 맞게 재구성했습니다.

결과

NavMeshAgent를 직접 제어하지 않고, AI Navigation의 AutoBraking, OffMeshLink, AreaMask 동작을 분석해 WheelCollider 차량 주행 로직으로 재구현했습니다. 기존 NavMesh 데이터를 경로 생성에 활용하여, 물리 차량의 자율 주행을 구현했습니다.
